# ADR-010: Multi-Turn Session Delivery

## Status

**Accepted** — 2026-06-25. Implementation: spec-010-multiturn-session-delivery.

**Builds on**: ADR-009 (tool-based delivery). **Supersedes**: none.

## Context

Spec-009 implements single-turn Kafka → OpenCode session delivery:
every Kafka message creates a new OpenCode session, runs the LLM, and
the response is published back. The sessionId is auto-generated by
OpenCode and embedded in the response envelope so the caller can
theoretically continue the conversation — but the plugin has no
mechanism to **resume** an existing session when a follow-up message
arrives.

Kolya (2026-06-25) requested the ability to continue a multi-turn
conversation by including the sessionId in the Kafka payload.
Use case: a chat backend that maintains a session per user across
multiple user messages routed through Kafka.

## Why this is a small change

OpenCode SDK already supports calling `session.prompt({path:
{id: existingSessionId}, body: {...}})` on any session — internally,
OpenCode manages message history per session. When we call prompt on
the existing sessionId, OpenCode:
- Injects all previous user/assistant messages into the LLM context
- Runs the LLM with the new prompt
- Appends the new turn to the session's message history
- Fires `session.idle` event when done

This means the plugin needs to do **only one new thing**:
accept sessionId from Kafka payload and pass it to the existing
session.prompt() call instead of calling session.create() first.

## Considered alternatives

### Alternative 1: Tool-based resume (chosen)

**Approach**: Plugin reads sessionId from payload, verifies via
`client.session.get({path: {id}})`, passes existing sessionId to
`session.prompt()`. OpenCode handles message history automatically.

**Pros**:
- Minimal code change (~150 lines total: schema + 1 new module +
  adapter branch + consumer propagation)
- Leverages OpenCode's existing session management
- Backwards compatible: payloads without sessionId work as before
- Constitution Principle IV preserved: no new module-level state

**Cons**:
- One extra SDK round-trip per message (session.get lookup) — NFR-2:
  <5ms typical
- New failure mode (session not found, network error on get)
  requires graceful fallback

### Alternative 2: Separate "resume session" Kafka topic

**Approach**: External producer sends resume requests to a different
Kafka topic with `sessionId: "ses_xxx"`. Plugin subscribes to both
`opencode.prompts` (new conversations) and `opencode.resume`
(continuation requests).

**Pros**: clear separation of concerns.

**Cons**: Breaks existing producer interfaces. Requires producers to
know which topic to use. Adds Kafka topic management overhead.

**Verdict**: Rejected — Kolya's use case is the SAME topic for both
new and continuation messages, distinguished by presence of
sessionId field.

### Alternative 3: Multi-message session resume via in-memory Map

**Approach**: Plugin keeps Map<sessionId, lastSeenTimestamp> in
module scope. Kafka messages with sessionId "more than N seconds
old" are rejected (session expired).

**Pros**: Simple in concept.

**Cons**: Violates Constitution Principle IV (no cross-message
state). Doesn't actually solve anything — OpenCode itself manages
session lifetime, we shouldn't duplicate.

**Verdict**: Rejected — module-level state is anti-pattern per
Constitution.

## Decision

**Alternative 1 (tool-based resume) adopted.**

Implementation:
1. `RuleV003Schema` gains `resumeFromPayloadField?: string | null`
   (default `"sessionId"`, set `null` to disable resume per rule).
2. New `src/session-resume.ts` module with three helpers:
   - `extractSessionId(payload, rule)` — pure function, JSONPath extract
   - `verifySessionExists(client, sessionId)` — SDK session.get lookup
   - `decideResume(client, existingSessionId, rule)` — orchestrates
     extract+verify, returns `ResumeDecision`
3. `OpenCodeAgentAdapter.invoke()` accepts optional
   `existingSessionId?: string` in `InvokeOptions`. When provided,
   calls `decideResume()` first; if decision is `resume-existing`,
   skips `session.create()` and uses existing sessionId in
   `session.prompt({path: {id: existingSessionId}, body: {...}})`.
4. `eachMessageHandler()` extracts sessionId from payload using rule's
   `resumeFromPayloadField` JSONPath and passes it to `agent.invoke()`
   via the new `existingSessionId` field.
5. Response envelope gains `resumed?: boolean` flag indicating
   whether this turn resumed an existing session.
6. DLQ envelope gains `resumeAttempted?: boolean` + `attemptedSessionId`
   for diagnosing resume failures.

## Consequences

### Positive
- Multi-turn chat-from-Kafka now possible (Kolya's use case)
- Backwards compatible: existing payloads without sessionId work
  unchanged (default `"sessionId"` JSONPath + graceful fallback to
  new session on lookup failure)
- Constitution Principle IV preserved: no module-level state for
  sessions (only ephemeral `SessionWatcher` Map already exists)
- Architecturally small: ~150 LOC across schema + 1 module +
  adapter branch + consumer propagation

### Negative
- New failure modes (session not found, network error on get)
  require graceful fallback — handled with logged warning + new
  session. Mitigation: `session_resume_failed` log event for
  observability.
- Latency: one extra SDK round-trip per message (~5ms in-process).
  Mitigation: NFR-2 documents acceptable threshold.
- Two concurrent messages with same sessionId could race. Mitigation:
  rule.concurrency (default 1) serializes; second message waits
  for first via Kafka offset ordering.

## Migration from spec-009

Existing `kafka-router.json` configs work unchanged. Existing
payloads without `sessionId` field default to `"sessionId"` JSONPath,
which returns null → fall back to new session (spec-009 behavior).
No breaking changes.

## When NOT to apply this decision

If OpenCode SDK removes or breaks `session.get()` (e.g., 2.x major
version), spec-010 resume path will need a different verification
mechanism. Until then, this implementation is stable.
