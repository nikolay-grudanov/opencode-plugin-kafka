# Feature Specification: Multi-Turn Session Delivery

**Feature Branch**: `010-multiturn-session-delivery`
**Created**: 2026-06-25
**Status**: Draft
**Input**: "Хочу чтоб опционально можно было в Kafka сообщении передать ид сессии чтоб отправить сообщение в диалог и продолжить общение с агентом."

**Builds on**: spec-009-tool-based-response-delivery (tool-based delivery,
session.idle event hook, plugin-level toggles).

**Supersedes**: None (additive feature).

## Context and Motivation

Spec-009 implements **single-turn** message handling: every Kafka
message creates a **new** OpenCode session, runs the LLM, and the
response is published back. The sessionId is auto-generated by OpenCode
and embedded in the response envelope so the caller can theoretically
continue the conversation — but the plugin has no mechanism to
**resume** an existing session when a follow-up message arrives.

This spec adds **multi-turn** capability: if the Kafka payload
contains a `sessionId` field, the plugin resumes that session (continues
the existing LLM conversation with full message history) instead of
creating a new one. If `sessionId` is absent or invalid, behavior is
identical to spec-009 (new session).

**Use case** (from Kolya 2026-06-25): external producer sends a Kafka
message with a JSON payload `{task: "...", sessionId: "ses_xxx"}`.
If the plugin has previously created session `ses_xxx` and that
session still exists in OpenCode, the LLM continues the dialog with
context of all previous messages. Otherwise the plugin falls back to
creating a new session.

**Why this matters for spec-009 architecture**: the tool handler
already uses `ctx.sessionID` from OpenCode SDK tool context. If we
resume an existing session, OpenCode will:
- Inject all previous messages into the LLM prompt automatically
- Track the new assistant turn in the same session
- Fire `session.idle` event for the same session when the new turn
  completes (so our existing safety net works without modification)

This means the change is **architecturally small** — the hard work
(message history, tool invocation, session.idle event) is already
done by OpenCode. We just need to:
1. Accept `sessionId` in Kafka payload
2. Pass it to `session.prompt({path: {id: sessionId}})` instead of
   the freshly-created sessionId
3. Verify the session still exists via `session.get({path: {id}})`
   before resuming
4. Fall back to new session if `session.get()` fails

## Compatibility with spec-009

This spec does **not** change:
- `matchRuleV003()` / `buildPromptV003()` — pure routing logic unchanged
- `agentId` flow — each rule still maps to one OpenCode agent
- Tool-based delivery — `send_to_kafka_*` tools work identically for
  resumed sessions (OpenCode handles message history automatically)
- `session.error` observability hook — unchanged
- `eventHook` safety net (session.idle → DLQ or fallback) — works for
  resumed sessions automatically
- Plugin-level toggles — unchanged
- DLQ flow — unchanged (resumed-session errors still go to DLQ)

This spec adds:
- **Per-rule** `resumeFromPayloadField?: string` config — names the
  JSON path in the Kafka payload where `sessionId` is read (default
  `sessionId`). Set to `null` to disable resume for that rule.
- **Kafka payload contract**: payload may include `sessionId` string
  at the configured JSONPath. If present and session exists → resume.
  Otherwise → new session.
- **`OpenCodeAgentAdapter.invoke()` signature**: gains optional
  `existingSessionId?: string` parameter. When provided, the adapter
  verifies the session via `session.get()` and uses it instead of
  creating a new one.
- **Response envelope**: existing `sessionId` field. For new sessions,
  this is the freshly-created ID. For resumed sessions, this is the
  same ID the caller passed in (echo for confirmation).
- **`fallbackToTextCapture` interaction**: when resuming, the captured
  text replaces only the latest assistant turn; previous turns are
  unchanged in OpenCode's internal history.

## User Scenarios & Testing *(mandatory)*

### User Story 6 — Multi-Turn via Payload sessionId (Priority: P1) 🎯 MVP

As an external Kafka producer (e.g., a chat backend or workflow
orchestrator), I want to send a follow-up message to an existing
OpenCode session by including the `sessionId` in the Kafka payload.
The plugin should resume the existing session so the LLM has full
context of previous turns, instead of starting from scratch.

**Why this priority**: Core feature requested by Kolya. Enables
stateful chat-from-Kafka workflows (e.g., a Slack bot that maintains
context across multiple user messages routed through Kafka). Without
this, every Kafka message is a fresh conversation — useless for
real-world chat applications.

**Independent Test**: Produce message1 → receive response with
sessionId → produce message2 with same sessionId → verify the plugin
resumed the existing session (not created a new one) and the LLM
context was preserved (visible via OpenCode logs: same sessionID in
`loop session.id=ses_xxx step=N` lines, history grew with both user
messages).

**Acceptance Scenarios**:

1. **Given** Kafka message `{task: "Remember: my name is Alice"}`
   arrives on `opencode.prompts`, **When** the plugin processes it,
   **Then** a new OpenCode session `ses_xxx1` is created, the LLM
   responds (e.g., "OK Alice"), and the response envelope contains
   `sessionId: "ses_xxx1"`.

2. **Given** the previous response with `sessionId: "ses_xxx1"` and
   Kafka message `{task: "What's my name?", sessionId: "ses_xxx1"}`
   arrives on `opencode.prompts`, **When** the plugin processes it,
   **Then** the plugin verifies `ses_xxx1` still exists in OpenCode,
   resumes it, and calls `session.prompt({path: {id: "ses_xxx1"}})`
   (not a new `session.create()`). The LLM sees both user messages in
   context and responds with "Alice".

3. **Given** Kafka message `{task: "...", sessionId: "ses_dead"}`
   where `ses_dead` was never created or has been deleted from
   OpenCode, **When** the plugin processes it, **Then** the plugin
   logs a warning (`session_resume_failed sessionId=ses_dead
   reason=not_found`), creates a new session, and the response
   envelope contains a fresh `sessionId`.

4. **Given** Kafka message `{task: "..."}` (no sessionId field),
   **When** the plugin processes it, **Then** the plugin behaves
   identically to spec-009 (creates a new session, returns its ID in
   response envelope).

5. **Given** Kafka message `{task: "...", sessionId: 12345}` (numeric,
   not string), **When** the plugin processes it, **Then** the plugin
   logs a warning (`session_id_not_string valueType=number`) and falls
   back to creating a new session (no crash, no DLQ).

6. **Given** a rule with `resumeFromPayloadField: null` (resume
   disabled for this rule), **When** a Kafka message arrives with
   `sessionId`, **Then** the plugin ignores the field and creates a
   new session.

### User Story 7 — Mixed Multi-Turn Sessions (Priority: P2)

As a Kafka producer, I want multiple independent multi-turn
conversations to coexist without interference. Each conversation has
its own sessionId; the plugin routes each message to the correct
session.

**Why this priority**: Real-world chat systems have many concurrent
users. Each user has their own session; Kafka messages must not
cross-contaminate.

**Independent Test**: Produce two messages with different sessionIds
in interleaved order (e.g., msg1 for user A, msg2 for user B, msg3 for
user A, msg4 for user B). Verify each session has only its own
messages in OpenCode history (check via `session.messages()`).

**Acceptance Scenarios**:

1. **Given** two concurrent sessions `ses_aaa` and `ses_bbb`,
   **When** messages arrive interleaved (A1, B1, A2, B2), **Then**
   the plugin routes each to the correct session and OpenCode keeps
   two independent message histories.

2. **Given** a session that exceeded its `maxSessionMs` (force-DLQ'd
   by the safety net), **When** a new Kafka message arrives with the
   same sessionId, **Then** the plugin verifies the session — it's
   still in OpenCode memory (the watcher cleaned up but the session
   itself wasn't deleted) — and resumes successfully.

### Edge Cases

- What happens when the resumed session has a different `agentId`
  than the rule expects? OpenCode allows changing agent mid-session.
  Decision: trust the Kafka payload; if sessionId exists, resume even
  if agent differs (caller knows what they're doing).
- What happens when multiple Kafka messages with the same sessionId
  arrive concurrently? Spec-009 already serializes via rule
  `concurrency`; spec-010 inherits this. The second message waits
  until the first completes (OpenCode handles message ordering).
- What happens when the resumed session was started by another
  OpenCode instance (not our plugin)? We still resume — sessionId is
  a global OpenCode identifier.
- What if `session.get()` returns the session but its status is
  "idle" or "busy"? Spec-009 already handles both (prompt can be
  called on any non-deleted session).
- What if the Kafka payload contains both `sessionId` and a
  conflicting rule configuration? `sessionId` wins (caller intent
  takes precedence).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1**: `RuleV003Schema` accepts a new optional field
  `resumeFromPayloadField: z.string().nullish()` (default `"sessionId"`).
  When set to `null` or empty string, the rule does NOT resume —
  always creates a new session (spec-009 behavior).

- **FR-2**: The plugin MUST extract `sessionId` from the Kafka payload
  using the rule's `resumeFromPayloadField` JSONPath. If the field is
  absent, non-string, or empty, the plugin MUST create a new session
  (no warning unless value type is wrong).

- **FR-3**: When `sessionId` is extracted and non-empty, the plugin
  MUST call `client.session.get({path: {id: sessionId}})` to verify
  the session exists. If `session.get()` returns an error or null
  result, the plugin MUST log a warning and create a new session
  (graceful fallback).

- **FR-4**: When the session exists, the plugin MUST call
  `client.session.prompt({path: {id: sessionId}, body: {agent,
  parts}})` — using the **existing** sessionId instead of the freshly
  created one. The plugin MUST NOT call `session.create()` in this
  path.

- **FR-5**: `OpenCodeAgentAdapter.invoke()` MUST accept an optional
  `existingSessionId?: string` parameter in `InvokeOptions`. When
  provided, the adapter MUST verify the session via `session.get()`
  and use the existing session. When omitted or invalid, the adapter
  MUST fall back to creating a new session (spec-009 behavior).

- **FR-6**: The response envelope (DLQ and responseTopic producers)
  MUST always include a `sessionId` field. For new sessions, this is
  the freshly-created ID. For resumed sessions, this is the same ID
  the caller passed in. The `kafka_message_lifecycle` event MUST log
  the `phase: "session_resumed"` step for resumed sessions and
  `phase: "session_created"` for new ones.

- **FR-7**: The plugin MUST NOT introduce new module-level state for
  session tracking. Session lookup MUST be performed on every
  Kafka message via `client.session.get({path: {id}})`. Constitution
  Principle IV (No-State Consumer) is preserved.

- **FR-8**: When a Kafka message specifies a sessionId that already
  has an active `SessionWatcher` (from a concurrent message in the
  same plugin instance), the plugin MUST wait for the watcher to
  release (concurrency=1 by default) OR create a new session. The
  resolution MUST be logged. Spec-009's `session_watcher_already_exists`
  warning (during live debug) is the symptom — spec-010 fixes it by
  using the watcher map for coordination.

### Non-Functional Requirements

- **NFR-1 (Backwards compat)**: Existing Kafka payloads without
  `sessionId` field work identically to spec-009. Existing
  `kafka-router.json` configs without `resumeFromPayloadField` field
  default to `"sessionId"` (resume enabled, looks for the standard
  field name).

- **NFR-2 (Performance)**: The `session.get()` check adds one
  round-trip to the OpenCode SDK per Kafka message (typically <5ms
  in-process). No measurable impact on throughput.

- **NFR-3 (Observability)**: Resume path MUST log structured events:
  `session_resume_attempted sessionId=X`, `session_resume_succeeded
  sessionId=X`, or `session_resume_failed sessionId=X reason=...`.

- **NFR-4 (Constitution)**: Constitution Principle IV (No-State
  Consumer) is preserved — no cross-message session state in
  module-level Maps (except the existing bounded `SessionWatcher`
  Map, which is per-session ephemeral state). The session lookup is
  always fresh from OpenCode.

- **NFR-5 (Test coverage)**: Unit test coverage for new code
  (`session-resume.ts`, adapter resume branch) MUST be ≥90%.

### Key Entities *(see data-model.md for full schema)*

- **ResumeDecision** — enum: `"new" | "resume-existing" | "resume-fallback-new"`.
  Result of sessionId extraction + `session.get()` lookup.
- **SessionLookupResult** — discriminated union: `{found: true,
  sessionId}` | `{found: false, reason: "not-found" | "lookup-error"}`.
- **SessionEventLog** — extends `kafka_message_lifecycle` with new
  phases: `"session_created"`, `"session_resumed"`, `"session_lookup_failed"`.

## Out of Scope

- **Multi-session per rule** — one Kafka message still maps to one
  OpenCode session. Multi-turn means follow-up messages use the same
  session; not parallel sessions per message.
- **Cross-plugin session sharing** — sessions created by this plugin
  CAN be resumed by other OpenCode SDK consumers (because sessionId
  is global), but this spec does not add APIs for that.
- **Session lifecycle management** — when to delete a session is up
  to OpenCode's compaction/session management. The plugin only
  resumes; cleanup is not its concern.
- **WebSocket / SSE streaming** — Kafka delivery is request-response
  per message, not streaming.
- **Tool `send_to_kafka_*` schema changes** — the existing tool
  already returns `sessionId` in its result (via `ctx.sessionID`);
  no schema change needed.

## Open Questions *(resolve before /speckit.clarify if needed)*

1. Should the plugin expose a tool `list_sessions` or
   `get_session_history` so the LLM can introspect previous turns?
   Out of scope for this spec (future spec 011+).
2. Should there be a per-rule `maxResumedTurns` cap to prevent
   unbounded session growth? Out of scope; OpenCode has its own
   compaction mechanism.
3. When a resumed session has stale tool definitions (e.g., plugin
   was updated while session was alive), should the plugin warn?
   No — OpenCode handles tool registration per session.

## Acceptance Criteria Summary

- [ ] Kafka message without sessionId field → new session, response
  envelope contains fresh sessionId.
- [ ] Kafka message with valid sessionId and existing session →
  session resumed, response envelope echoes the same sessionId.
- [ ] Kafka message with invalid/expired sessionId → warning logged,
  new session created, response envelope has fresh sessionId.
- [ ] Rule with `resumeFromPayloadField: null` → ignores sessionId,
  always new session.
- [ ] Two concurrent sessions (A, B) with interleaved messages →
  each session has its own independent message history.
- [ ] All existing spec-009 tests pass unchanged (FR-1 backwards
  compat default `"sessionId"` is a no-op when payload has no such
  field).
- [ ] Live debug: produce msg1, observe sessionId in response,
  produce msg2 with that sessionId, observe continued session in
  OpenCode logs (same sessionID, history grew).
